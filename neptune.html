NEPTUNE: IPv6 Multihoming Architecture for Residential Multi-ISP Networks

2024 • IPv6, Multihoming, DHCPv6-PD, NPTv6, Protocol Design

Introduction and Statement of the Problem

To this day, the networks around the world still operate over Internet Protocol version 4, commonly known as IPv4. In fixed Internet access, the most common deployment is having a single public address assigned to the home or company router, giving private addresses to the hosts (PCs and servers), and using NAT (Network Address Translation) to allow these hosts to connect to the Internet. This setup was not intended to be used in the original Internet Protocol proposal; it was born as a temporary workaround to the exhaustion of the IPv4 address space, which makes it impossible to assign a public IP to each end device. This method, however, does not work well with some remote services, such as point-to-point VPNs.

The IPv6 protocol emerges as an evolution of IPv4, having a much larger addressing space (2128 vs 232), and coming together with specific auxiliary protocols for address assignment and automatic host configuration. This tackles the public addressing issue, but its implementation brings other problems, as when it was proposed the world was already running over IPv4.

A key limitation arises from the fact that IPv4 and IPv6 are not interoperable, meaning that a node in an IPv6-only network will not be able to communicate with another node in an IPv4-only network, even if they are physically reachable. For those scenarios, we need to use the so-called transition mechanisms, designed to allow a smooth transition between the two addressing spaces.

However, none of these protocols address a very common setup in small to medium-size businesses: using multiple Internet connections at once, known as multihoming. In an IPv4 setup with NAT, it is easy to divide the traffic flow by dynamically adjusting which connections are translated to each of the public IP addresses. With IPv6, on the other hand, you would need to assign an address from each of the circuits provided to every host. This eliminates any possibility of applying balancing policies and requires a reconfiguration of the whole network (revoking one of the prefixes assigned) in the event of a circuit failure, causing inconvenient downtime.

Combining IPv4 and IPv6 networks complicates even more the management of these deployments. To date, there is not an official nor proprietary method to address these issues.

The Network Prefix Translation Unified Environment, NEPTUNE from now on, defines a suite of protocols and mechanisms to allow for a smooth network deployment and management, unifying traffic shaping, address translation and load balancing.

State of the Art

The closest approach for what this project aims to solve is described in section 3.2.4, Multihoming, of RFC 7368 (2014) – IPv6 Home Networking Architecture Principles. While it does not address in a global way the issues related to multi-ISP deployments, it gives examples for simple setups, and leaves the door open to future improvements:

However, the general multihoming problem is broad, and solutions suggested to date within the IETF have included complex architectures for monitoring connectivity, traffic engineering, identifier-locator separation, connection survivability across multihoming events, and so on. It is thus important that the homenet architecture should as far as possible minimize the complexity of any multihoming support. (RFC 7368, 2014, section 3.2.4)

Some existing protocols will be used in order to define and implement NEPTUNE. These protocols and their roles will be described in greater detail along the project:

1. IPv6-Specific Protocols

  • DHCPv6 – Dynamic Host Configuration Protocol v6 (RFC 8415)
    In IPv6, DHCP is used only by the ISP, to delegate an address prefix to each customer. This technique is known as DHCPv6-PD (Prefix Delegation).
  • RA – Router Advertisement (RFC 4861)
    The router sends ICMPv6 messages to the hosts, announcing the network prefix so they can acquire an address.
  • SLAAC – Stateless Address AutoConfiguration (RFC 4862)
    Hosts autogenerate an address inside the announced prefix. A DAD (Duplicate Address Detection) message is broadcast to ensure uniqueness.
  • NPTv6 – Network Prefix Translation v6 (RFC 6296)
    Allows stateless translation between IPv6 prefixes. Rarely used today, but essential for NEPTUNE’s design.

2. IPv6 Transition Mechanisms

  • DS – Dual Stack (RFC 4213)
    Parallel IPv4 and IPv6 networks. Full compatibility but double address space.
  • DS-Lite – Dual Stack Lite (RFC 6333)
    ISP network runs IPv6-only; customer LAN runs IPv4-only. Uses NAT46 + NAT64. Does not provide native IPv6 connectivity to the host.
  • 464XLAT (RFC 6877)
    Common in mobile networks. Hosts generate IPv4-embedded IPv6 addresses, and the ISP de-translates them to reach IPv4 services. Offers native IPv6 to hosts.

Motivation

The rapid growth of devices connected to the Internet is beginning to expose the limitations of the IPv4 infrastructure. Regardless of how powerful the hardware is on paper, the lack of public addresses per device complicates the logical operation of certain point-to-point services and makes others completely unavailable.

This, together with the lack of a protocol to address such a common setup as multi-ISP load balancing for IPv6, creates a perfect gap for NEPTUNE to fill.

Therefore, the aim of the project is not to cover a need yet to be created, but to address a real, existing problem that slows down the evolution of Internet architectures.

Aim of the Project

  1. To analyze the current limitations of existing IPv6 protocols, identifying the challenges that hinder certain deployment scenarios.
  2. To enable a seamless transition from IPv4 towards IPv6, ensuring interoperability and preserving end-to-end communication in mixed environments.
  3. To propose a de-facto standard for IPv6 deployments, defining NEPTUNE as a unified framework to simplify traditionally complex configurations.

Preliminary Proposal

NEPTUNE is a project currently under development. The following section provides a brief description of how the protocol is intended to operate, in conjunction with the architecture shown in the diagram below.

Network clients may have the following types of addresses in their network stacks, listed in order of preference:

  1. IPv6 public: automatically configured via RA + SLAAC.
    • If more than one ISP (and therefore more than one delegated prefix) is present, only one prefix will be advertised internally. A 1:1 NPTv6 mapping table among prefixes will be maintained by the Prefix Engine for inter-prefix translation.
  2. IPv4 public: statically assigned to selected hosts when an IPv4 BGP circuit exists.
  3. IPv4 private: assigned statically or via DHCP when an IPv4 NATed circuit is present.
  4. IPv6 private (ULA): only generated when M:1 NATv6 is required.
    • For example, a 5G modem used as a backup connection may only provide a single IPv6 address via 464XLAT.

The DNS Engine will process DNS queries and generate synthetic responses whenever translation is required. Latency and reliability metrics derived from these queries will also feed the Load Balancer to influence circuit weighting and selection.

The NEPTUNE Virtual Interface acts as a sink for all outgoing LAN traffic. The NEPTUNE Core then handles balancing, translation and encapsulation of flows based on:

  • The IP capabilities of the remote host (IPv4/IPv6).
  • The available circuits and their current health state.
  • The configuration and applied policies.

Main scenarios

  • Host → IPv6-capable server (multi-flow): Flows are distributed across all IPv6-capable circuits according to real-time link conditions. Each flow remains pinned to its circuit to preserve return-path symmetry.
  • Host → IPv6-capable server (single-flow): The Load Balancer selects the best circuit at connection setup. 5-tuple stickiness can be disabled to allow spreading a single connection across circuits, though it remains enabled by default to avoid breaking P2P-style services.
  • Host → IPv4-only server (multi-flow): If the host has a static public IPv4 assigned via BGP, that circuit is prioritised. Otherwise, load is split across all IPv4-capable circuits.
  • Host → IPv4-only server (single-flow): If a static public IPv4 exists, it is used. Otherwise the Load Balancer selects the best IPv4-capable circuit given current link conditions. Stickiness may be disabled if required.

The translator/encapsulator modules perform the required transformations (NPTv6, NAT44, NAT46/NAT64) and manage packet encapsulation and decapsulation.

All policies configured through the NEPTUNE CLI/GUI are stored and enforced by the Policy Engine, which communicates directly with all core modules. The data plane and control plane are strictly separated. A dedicated Telemetry Module continuously logs circuit health, performance metrics and relevant operational events to provide observability and aid debugging.
