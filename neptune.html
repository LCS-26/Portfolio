NEPTUNE: IPv6 Multihoming Architecture for Residential Multi-ISP Networks

2024 • IPv6, Multihoming, DHCPv6-PD, NPTv6, Protocol Design

Summary

NEPTUNE is a protocol architecture designed to enable reliable, deterministic and fully compatible IPv6 multihoming in residential and small-office networks using multiple ISPs simultaneously, without requiring hardware changes or non-standard mechanisms.

Current IPv6 deployments still lack a practical solution for prefix stability, multi-ISP coexistence, and seamless failover, often forcing users to depend on IPv4, NAT, or hybrid transition mechanisms that compromise performance and reliability.

This project proposes a standards-aligned architecture that coordinates Prefix Delegation, stateless prefix translation (NPTv6), router advertisement control, and ISP-health monitoring, enabling a stable internal addressing plan independent of external ISP changes. The design is validated through software simulation that models ISP revocation, failover, and real-world prefix instability scenarios.

Motivation

Despite widespread IPv6 deployment, real multihoming remains largely unsolved in residential networks:

  • ISPs delegate IPv6 prefixes dynamically, with no guarantee of stability.
  • Hosts configure global IPv6 addresses via SLAAC or DHCPv6, tightly coupling their identity to the ISP-assigned prefix.
  • Using two ISPs simultaneously yields multiple valid prefixes but no coordination mechanism between them.
  • When an ISP revokes or changes its prefix, the internal addressing structure becomes invalid, forcing renumbering.
  • Unlike IPv4, IPv6 typically avoids NAT, removing the “stable private address” layer that users rely on.

NEPTUNE was developed to bridge this gap by delivering:

  • Stable internal IPv6 addressing independent of ISP prefix volatility.
  • Multi-ISP coexistence without renumbering LAN devices.
  • Deterministic and controlled failover.
  • Compatibility with existing standards, hardware and ISP behaviour.
  • A transition path for networks using mixed IPv4/IPv6 mechanisms.

Requirements

Technical Requirements

  • Support for multiple ISPs with independent IPv6 Prefix Delegation (IA_PD).
  • Compatibility with dual-stack networks and mechanisms such as NAT44, DS-Lite, 464XLAT and MAP-E.
  • Ability to generate and maintain a stable internal prefix resilient to ISP prefix changes.
  • Deterministic, reversible stateless prefix translation (NPTv6) between internal and ISP prefixes.
  • Full compatibility with existing host mechanisms: SLAAC, Router Advertisements (RA), DHCPv6-PD.
  • No changes to packet formats or non-standard encapsulations.

Operational Requirements

  • Transparent failover when one ISP becomes unreachable or revokes its prefix.
  • No manual reconfiguration on client devices during ISP transitions.
  • Consistent addressing for always-on devices (servers, IoT, smart home systems).
  • Observability of prefix health, ISP status and translation behaviour.

Constraints

  • ISP prefix delegation is dynamic and cannot be controlled from the customer side.
  • Many residential ISPs do not offer static IPv6 prefixes.
  • Client devices are not designed to handle frequent renumbering or rapid prefix replacement.
  • No changes can be made to ISP networks; the solution must reside at the CPE / edge.

Design

Prefix Orchestrator

The Prefix Orchestrator manages all delegated IPv6 prefixes obtained from each ISP via DHCPv6-PD. It maintains a live table with:

  • Currently active delegated prefixes per ISP.
  • Health state and reachability of each ISP.
  • Priority and selection metrics for each upstream.
  • History of prefix changes and revocations.

When an ISP changes or revokes its prefix, the orchestrator coordinates a controlled transition without exposing instability to the LAN.

Internal Stable Prefix

NEPTUNE introduces a stable internal prefix that remains constant regardless of which ISP is currently active or which prefix has been delegated. For example: 

Internal prefix: fd00:1234:abcd::/48
ISP prefix 1:   2a02:xxxx:xxxx::/56
ISP prefix 2:   2a10:yyyy:yyyy::/56

LAN hosts only see and use the internal prefix. This avoids renumbering, improves device stability, and provides a deterministic basis for failover and multi-ISP operation.

Stateless Prefix Translation (NPTv6)

Stateless prefix translation using NPTv6 provides a checksum-neutral, reversible 1:1 mapping between the internal prefix and each ISP prefix: 

[Internal prefix]  <-->  [ISP prefix]

This translation:

  • Preserves host identifiers under each mapping.
  • Requires no per-flow state.
  • Automatically adapts to changing ISP prefixes.
  • Enables true IPv6 multihoming without introducing NAT66 semantics.

Each ISP is associated with its own NPTv6 translation instance, which can be enabled or disabled according to ISP health.

Router Advertisement Control Plane

NEPTUNE centrally manages Router Advertisements to ensure:

  • LAN hosts always see the internal prefix as on-link and valid.
  • Default routes are advertised via virtual routers, decoupled from specific ISPs.
  • Failover is expressed as route metric changes, not as prefix replacement.

This avoids RA storms, abrupt deprecation of prefixes and other disruptive behaviours observed in naive dual-ISP IPv6 setups.

Link-Health & Decision Engine

The decision engine continuously monitors:

  • Reachability of each upstream (probe-based health checks).
  • DHCPv6-PD renew and rebind behaviour.
  • Prefix revocation or delegation failures.
  • Latency and packet loss per ISP.

Upon detecting an ISP failure, it:

  • Detaches the failed ISP from active routing and translation.
  • Adjusts route metrics to prefer healthy ISPs.
  • Activates only the corresponding NPTv6 translation instances.
  • Preserves the internal addressing model on the LAN.

Implementation

A software-based simulator was developed to validate NEPTUNE’s behaviour under realistic multi-ISP conditions. The simulator models:

  • A virtual router implementing DHCPv6-PD handling, NPTv6 translation and router advertisement control.
  • Multiple ISPs with dynamic prefix delegation and revocation events.
  • Transient ISP failures, restorations and prefix changes.
  • Client devices obtaining addresses using SLAAC under the internal stable prefix.

Functional components implemented include:

  • Prefix Delegation Processor for IA_PD lifecycle and timers.
  • NPTv6 Translator for checksum-neutral, stateless prefix mapping.
  • ISP Simulation Module to emulate real-world prefix churn and outages.
  • RA Daemon to manage the internal prefix and default route advertisements.
  • Failover Engine implementing the decision logic across ISPs.

Results

Simulation results show that NEPTUNE:

  • Maintains stable LAN addressing even under frequent ISP prefix changes.
  • Achieves immediate failover when an ISP becomes unreachable or revokes its prefix, without requiring client reconfiguration.
  • Ensures correct NPTv6 translation for all outbound flows during ISP transitions, maintaining consistency and reachability.
  • Avoids any renumbering events on LAN devices during failover scenarios, preserving IPv6 identities.
  • Remains compatible with existing ISP behaviour, RFC-compliant DHCPv6-PD and NPTv6 implementations.

The architecture scales naturally to more than two ISPs and can be deployed on commodity hardware (for example, OpenWrt-based routers) with appropriate software support.

What I Learned

  • Designing a multihoming architecture is fundamentally a control-plane problem that requires coordinated behaviour across addressing, routing and failure detection.
  • IPv6 mechanisms such as SLAAC, RA and DHCPv6-PD introduce real-world constraints that are not obvious from theoretical descriptions, especially in multi-ISP environments.
  • Stateless prefix mapping with NPTv6 is powerful, but must be integrated carefully to avoid routing loops, asymmetric paths or policy conflicts.
  • Building a simulation environment was essential to validate the design, revealing edge cases that would be hard to detect with purely analytical reasoning.
  • Providing IPv4-like stability (as offered by NAT) in IPv6 networks is still a key requirement for many residential scenarios; NEPTUNE offers this stability while remaining fully standards-compliant.
